# 배포 PC Codex용 부하 시험 및 자원 모니터링 요청

BabyEye를 운영하는 Windows Docker Desktop PC에서 부하 시험과 결과 요약을 진행해줘. 운영 저장소는 C:\deploy\baby-monitor, GitHub는 https://github.com/ImSChan/baby-monitor.git 이야.

목표는 API 응답시간·처리량·오류율과 함께 Windows/WSL2/Docker 메모리, 디스크 사용량·I/O를 측정하고 병목과 남은 검증 범위를 정리하는 것이야. 능력 확인이나 계획 제시에서 끝내지 말고 안전한 범위의 시험·관측·보고서까지 완료해줘.

## 1 기본 원칙과 분리
- AGENTS.md와 docs/LOCAL_LOAD_TEST_RESULTS.md, 실제 Compose 구성을 먼저 읽어. 운영 컨테이너·계정·비밀키·DB·업로드·학습 자료·가중치·백업·SSL 인증서를 보존해.
- 운영 자동 재배포, 컨테이너 재시작/재생성, 모델 승격, GPU 학습, DB 초기화, docker compose down -v, docker system prune, 파일 강제 삭제, git reset/clean은 하지 마.
- 기본 부하 대상은 같은 PC에 만든 별도 시험 환경이야. 운영 API에는 저빈도 health 관측만 하고 쓰기·대량 로그인·푸시 발송·과부하 요청을 보내지 마.
- 운영 checkout은 바인드 마운트로 실행 중일 수 있으므로 git pull로 소스를 바꾸지 마. remote를 확인하고 fetch한 최신 main을 별도 새 시험 폴더의 clone 또는 detach worktree로 준비해. 기존 폴더가 있으면 덮어쓰지 마.
- 시험 Compose는 별도 고유 project 이름, 별도 network, 별도 신규 PostgreSQL/Redis 볼륨, 충돌하지 않는 127.0.0.1 전용 API 포트를 사용해. 실제 운영 리소스와 볼륨·외부 DB를 공유하지 않는지 config와 inspect로 확인하고 나서 시작해.
- 운영 .env와 인증 토큰·Firebase 키·실제 아이 자료는 복사하지 마. 테스트 JWT 키와 합성 계정·데이터만 사용하고, PUSH_ENABLED=false, TRAINING_TRIGGER_ENABLED=false로 고정해. GPU 학습·분석 워커는 기본 실행하지 마. 사용자 가중치는 시험용 빈 폴더로 분리하고 운영 가중치를 읽거나 바꾸지 마.
- 기존 Docker 이미지 캐시를 활용할 수 있으나 운영 이미지 태그를 덮어쓰지 마. 실제 Docker context가 이 PC의 Docker Desktop인지 확인해. 다른 원격 엔진이면 중단하고 알려줘.

## 2 실제 DB를 쓰는 시험 준비
- PostgreSQL 16, Redis 및 실제 API 라우터를 갖춘 격리 환경을 사용해. 코드에서 사용하는 DB와 마운트가 시험 전용임을 다시 검증해.
- backend/tools/local_load_test.py와 load_server.py는 개발 PC의 임시 SQLite 시험 전용 도구야. 이를 그대로 실행한 결과를 운영 PostgreSQL 검증이라고 하지 마. 필요하면 시험 폴더에 PostgreSQL용 seed·부하 생성기·관측 스크립트를 추가해.
- API와 같은 이미지 또는 필요한 의존성만 갖춘 시험 이미지에 시험 소스를 연결하고, 자원 부족 없이 시작할 수 있는지 확인해. 대형 GPU 이미지 다운로드/빌드는 기본 시험에 필요하지 않아.
- 합성 계정 8개 이상, 계정당 분석 약 240개와 알림·피드백을 준비하고 전부 테스트 provenance로 표시해. 유효한 이메일 형식을 쓰고 실제 로그인 성공을 사전 확인해. 실제 고객 계정이나 데이터를 조회·수정하지 마.
- 처음에는 GET과 로그인만 시험하고, 저장 검증은 격리 PostgreSQL에서만 해. 피드백 재전송·같은 계정의 동시 응답·다른 계정 접근 거부를 확인하며 예상 409/404와 서버 5xx를 구분해.
- 업로드 저장 부하는 합성 JPEG/WAV로만 하고 전체 새 미디어를 기본 200MB 이하로 제한해. 추론 워커를 끈 경우 이 시험은 업로드·Redis 등록·디스크 저장 부하이며 실제 모델 추론 성능이 아니라고 표시해.

## 3 기준선과 연속 모니터링
모든 관측은 같은 타임스탬프·단계 이름으로 CSV 또는 JSONL에 5초 간격으로 남겨줘. 부하 전 2분, 시험 중 전체, 종료 후 2분을 측정해.
- Windows: 전체 CPU, 사용 가능 RAM·커밋 메모리, Docker/WSL2 관련 프로세스 메모리, 실제 시험 데이터와 Docker 디스크 이미지가 놓인 드라이브의 총/남은 용량.
- 디스크: 읽기/쓰기 bytes/sec, 가능한 경우 IOPS·읽기/쓰기 지연·대기열 길이. Get-Counter/Get-CimInstance 등 실제 지원되는 지표를 사용하고 로캘·권한 문제로 못 읽는 항목은 미측정이라고 명시해. 카운터 단위를 확인하고 초·밀리초를 혼동하지 마.
- Docker: 대상 컨테이너별 CPU, 메모리 사용/한도, Net I/O, Block I/O, PID, OOMKilled와 재시작 횟수. 누적 I/O는 시간 차분으로 속도를 계산하고 Windows/WSL2/컨테이너 메모리를 중복 합산하지 마.
- PostgreSQL/Redis: 격리 DB의 연결 수·대기/잠금·deadlock, Redis 메모리·처리량·큐 길이를 가능한 범위에서 기록해. 쿼리 본문이나 사용자 자료·비밀번호는 로그에 남기지 마.
- 운영 서비스는 자원 상태와 저빈도 health만 관측해 시험 때문에 기존 서비스 상태가 나빠지는지 감시해. 운영 워커 로그는 필요한 오류·자원 지표만 요약하고 개인정보를 복사하지 마.
- 준비한 합성 자료와 실제 시험으로 증가한 용량을 구분하고, CSV를 같은 측정 구간으로 맞춰 p95 지연과 메모리·I/O의 동시 변화를 비교해.

## 4 단계별 부하와 중단 조건
기본 계획은 아래와 같아. 이전 단계가 안정적일 때만 올리고 각 단계 시작/끝을 기록해.
1. 사전 정상 요청 확인과 1분 준비 부하.
2. 조회 API 혼합: 1→5→10→20 VU를 각 60초. 50 VU는 20 VU와 운영 health가 충분히 안정적일 때만 최대 60초.
3. 안정적으로 통과한 단계 중 최대 20 VU에서 5분 지속 시험.
4. 실제 비밀번호 검증 로그인: 동시 1→2→4, 각 30초. 인증 응답과 메모리 증가를 별도 집계.
5. 격리 DB 피드백 저장/충돌/재전송, 제한된 합성 미디어 업로드와 큐·디스크 증가량 측정.
6. 실제 WebSocket 시그널링: 최대 20세션/40연결 유지와 heartbeat, 조회 병행. 정리 후 잔여 세션이 없어야 해. 이 단계는 실제 영상 비트레이트 시험이 아니야.
7. 부하를 멈추고 2분 회복 관측. 메모리가 돌아오는지, 큐·연결·파일 핸들·세션이 남는지 확인해.

중단 기준은 시험 시작 전에 확인하고 보수적으로 적용해.
- 운영 health가 연속 2회 실패하거나, 기존 운영 컨테이너 OOM/재시작이 발생하면 즉시 부하 생성만 중단.
- 가용 RAM이 2GB 또는 총 RAM의 10%보다 작아지는 상태가 3회 관측되거나 시험 컨테이너 OOM이 발생하면 중단.
- 해당 데이터 드라이브 여유가 10GB 또는 10%보다 작으면 쓰기 시험을 시작하지 말고, 시험 중 그 기준에 이르면 중단.
- 전체 CPU 90% 초과가 30초 지속되거나 예상 밖 오류율 1% 초과/조회 p95 2초 초과가 30초 지속되면 단계 상승을 멈추고 회복 관측으로 전환. 이는 임시 안전 기준이며 운영 SLA라고 단정하지 마.
- 어떤 경우에도 장애 복구를 이유로 운영 DB·서비스를 자동 재시작하거나 원본 자료를 지우지 마. 종료할 때는 생성한 부하 프로세스와 시험 컨테이너만 정리하고, 결과 파일은 보존해. 시험 볼륨 삭제는 기본적으로 하지 마.

## 5 결과물과 최종 요약
시험 폴더 아래 results/<타임스탬프>에 다음을 남겨줘.
- 재현 명령·시험 코드·대상 버전과 구성, 단계별 시작/종료 시각.
- load_results.json/csv, host_metrics.csv, container_metrics.csv, 가능한 disk/db/redis 관측 자료, 비밀값을 제거한 오류 요약.
- REPORT.md와 SUMMARY.md. 수치를 추측하지 말고 실제 관측만 쓰며 미실행/미측정/중단 항목과 이유를 명시해.

최종 답변에는 아래 항목을 한국어로 요약해줘.
1. 시험이 실행됐는지, 범위·버전·시간·데이터 규모, 운영 데이터 변경 여부.
2. 단계별 VU·실측 시간·요청 수·RPS·p50/p95/p99·예상 밖 오류율 표. VU를 실제 사용자 수나 최대 수용량으로 환산하지 마.
3. 호스트/컨테이너 메모리 시작·최대·회복 후 값, OOM·재시작 유무. 짧은 시험만으로 누수 없음이라고 단정하지 마.
4. 드라이브 여유와 시험 증가량, 읽기/쓰기 속도·지연·대기열, DB/Redis 대기와 이상 여부. Docker VHDX 크기와 컨테이너 내부 사용량은 별도 수치로 구분.
5. 가장 먼저 지연된 경로와 같은 시간의 CPU·메모리·디스크 근거. 근거가 없으면 원인 미확정이라고 써줘.
6. 피드백 중복·소유권·충돌·세션 정리 결과와 미검증 GPU/실제 영상/FCM/Android 장시간 항목.
7. 다음 개선 우선순위 3개와 결과 파일 절대 경로.

개발 PC 참고값은 8개 합성 계정/1,920개 분석/임시 SQLite/단일 Uvicorn에서 측정 10,712건·예상 밖 오류 0건, 20 VU 60초 p95 445ms, 50 VU p95 1,349ms야. 생성기와 API가 같은 개발 PC였고 GPU·실제 PostgreSQL·영상 전송·FCM 성능 결과가 아니므로 배포 PC 결과와 동등 조건처럼 비교하지 마.
