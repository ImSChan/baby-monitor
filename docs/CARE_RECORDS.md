# 육아 기록과 월령별 보조 판단

## 사용자 경험

기존 ‘육아 기록’ 탭은 제거하고 홈의 ‘육아기록으로 더 정확하게 판단하기’ 입력 창으로 통합했다. 창 안에서 시간 입력/최근 기록/아이·설정을 관리한다. 같은 계정으로 로그인한 보호자 기기들이 같은 기록을 사용한다. 계정당 한 아이를 지원한다. 회원가입 또는 육아 기록 화면에서 아이 이름과 현재 월령(0~71개월)을 입력한다. KST 입력일을 기준으로 완료된 달 수만큼 추정 월령이 증가하며 생일을 수집하지 않는다. 과거 촬영 시점의 월령도 추정치다. 기존 계정에는 임의 월령을 채우지 않으며 정보가 없으면 AI 점수 보정을 하지 않는다. 여러 아이 구분은 포함하지 않는다.

- 식사: 이유식/수유/간식 선택 → 날짜·시각 선택 또는 ‘방금 먹었어요’ → 저장.
- 수면: 깬 날짜 선택 → 손가락으로 막대를 쓸어 시작~종료 구간 선택. 두 슬라이더로 5분씩 조절하거나 정확한 시각을 직접 입력한다. 이전 날부터의 구간도 표시하므로 자정을 넘긴 수면을 기록할 수 있다.
- 한 수면 기록은 최대 24시간이며 미래 시각/역전/중복 수면 구간은 거부한다. 24시간 제한은 입력 오류 방지용이지 권장 수면 길이가 아니다.
- 최근 7일 기록, 최근 식사/기상 시각, 지난 24시간에 **기록된** 수면 합계를 보여준다. 수정은 revision을 검사하고, 삭제 전 확인한다. 기록이 빠졌을 수 있으므로 합계만으로 수면 부족을 판정하지 않는다.
- ‘AI 판단에 육아 기록 참고’를 끌 수 있다. 설정/기록 변경은 이후 분석 요청부터 적용하며 이미 요청·완료된 분석의 스냅샷은 바꾸지 않는다.

## 근거와 구현 정책의 구분

초기 검토일: 2026-11-17. 아래 아이사랑 자료는 초기 10개월 정책의 근거다. 2026-11-24부터 입력 월령별 정책으로 확장했다.

- [아이사랑 수유·영양](https://www.childcare.go.kr/?menuno=449): 9~11개월 후기 이유식과 하루 3회 식사 안내를 제공한다.
- [아이사랑 건강과 일상](https://www.childcare.go.kr/?menuno=451): 규칙적인 식사와 보호자의 배고픔·포만 신호 관찰을 함께 안내한다. 이 페이지에 보편적인 ‘수유 후 몇 시간이면 배고픔’이라는 AI 진단 임계값은 없다.
- 수면 수치의 근거는 별도로 [CDC About Sleep](https://www.cdc.gov/sleep/about/)를 확인했다. 4~12개월에는 낮잠 포함 24시간 12~16시간을 안내한다. 아이사랑에서 확인하지 못한 수면 수치를 해당 사이트의 기준으로 표시하지 않았다.

위 안내는 화면의 참고 정보다. 식사량·성장·건강 상태가 없으므로 하루 횟수나 기록된 수면 합계로 요구를 확정하거나 식사/수면을 강요하는 기능을 만들지 않았다. 아래 점수/시간 값은 **검증된 의료 기준이 아닌 버전 관리된 엔지니어링 휴리스틱**이다. 임상적 정확도 향상을 입증한 것은 아니다.

월령별 일일 참고 정보는 [WHO 보완식 안내](https://www.who.int/health-topics/complementary-feeding), [CDC 수면 안내](https://www.cdc.gov/sleep/about/), [NIH 신생아 수면 안내](https://www.nichd.nih.gov/health/topics/sleep/conditioninfo/how-much)를 확인했다(2026-11-24). 6~8개월 보완식 2~3회, 9~23개월 3~4회, 수면 0~3개월 14~17시간/4~11개월 12~16시간/12~35개월 11~14시간/36~71개월 10~13시간을 참고로 표시한다. 하루 권장 수치를 AI용 고정 식사·기상 간격으로 환산하지 않는다.

## 실제 AI 처리

정책: care-age-v2 (2026-11-24). 기존 영상·소리 및 사용자별 모델 head 추론은 유지한다. 조용함/데이터 부족/낮은 점수로 normalOverride가 적용되거나 최종 stable이면 기록으로 판정을 뒤집지 않는다.

1. 서버가 인증된 사용자 소유 기록을 분석 요청 시각에 조회해 메타데이터에 고정한다. 클라이언트가 계산한 점수·다른 사용자의 ID·임의 context 객체는 받지 않는다.
2. 최대 과거 14일/최신 3000개 기록 중 촬영 시각 이전 기록만 사용한다. sleep 구간은 촬영 시각에서 잘라 합치며 중복 시간을 더하지 않는다. 과거 촬영 이후의 식사/기상 정보를 이전 시점의 판단에 사용하지 않는다.
3. 월령 단계(0~3/4~5/6~8/9~11/12~23/24~35/36개월 이상)를 분리한다. 같은 단계의 기록만 개인 간격에 쓰고, 가장 최근의 식사 종류(수유 또는 이유식)와 같은 종류끼리 간격을 계산한다. 6개월 미만은 이유식 기록을 보정에 쓰지 않는다. 0~3개월과 36개월 이상은 제품의 보수적 적용 범위로 시간 점수 보정을 끈다. 이 적용 범위는 의료기관의 진단 규칙이 아니다.
4. 기존 Top 2에 이미 있는 feeding/sleep 후보이고 원래 점수가 0.15 이상인 경우에만 보정할 수 있다. 없는 후보를 새로 만들지 않는다.
4. 최근 30분 내 이유식/수유 기록은 feeding 후보를 0.04 낮춘다. 섭취량을 모르므로 배고픔을 제외하는 규칙은 아니다. 간식은 규칙적인 주식 간격과 동일하게 취급하지 않는다.
5. 최소 4개의 유효한 기록 간격이 있어야 평소 간격의 중앙값을 계산한다. 같은 KST 날짜의 30~360분 간격만 사용해 야간 장시간/중복 입력의 영향을 줄인다. 이 제한도 의료 기준이 아니다.
6. 마지막 식사/기상 후 시간이 해당 개인 중앙값의 1.15배 이상이면서 8시간 이내이면 해당 모델 후보를 최대 0.06 높인다. 개인 간격이 없거나 아주 오래된/누락 가능성이 큰 기록은 시간 경과만으로 후보를 높이지 않는다.
7. 최소 15분 잠을 잔 뒤 30분 이내 기상 기록은 sleep 후보를 0.04 낮춘다. 촬영 시각이 기록된 수면 중이면 시간만으로 졸림 후보를 높이지 않는다.
8. 조정된 후보를 재정렬하므로 가까운 순위는 실제로 바뀔 수 있다. 점수는 보정된 예측 점수이며 의학적으로 보정된 확률이 아니다. 원래 모델 결과, 적용 여부, 변경 이유와 정책 버전을 careContext에 남긴다.

recordSetHash/recordCount와 계산된 간격·시각을 요청 메타데이터에 보존한다. 기록 수정·삭제 후에도 해당 분석의 기준은 재계산하지 않는다. 삭제는 soft delete로 이후 조회/판단에서 제외하고 감사용 원본과 기존 분석 근거는 보존한다.

**홈캠:** 촬영 시각을 알고 있으므로 새 앱이 care_context_allowed=true를 보내며 해당 시점의 서버 기록을 참고한다.

**업로드 영상:** 실제 촬영 날짜·시각을 입력했을 때만 허용한다. 비워 두면 업로드 시각은 기존 이력 표시용으로 사용하지만 오늘 기록을 과거 영상의 근거로 적용하지 않는다. 시간대 없는/미래 촬영 시각은 허용하지 않으며 30일보다 오래된 영상은 보조 판단을 건너뛴다. 기존 앱의 요청은 기본 false라 그대로 영상·소리 판단을 사용한다.

Analysis Worker의 기존 quiet override 이후, EmotionEvent 저장/3회 연속 알림 생성 이전에 보정한다. 따라서 홈·분석 결과·알림·돌아보기에서 같은 최종 상태를 사용한다. /api/emotions/history, dashboard, inference history/result에도 careContext를 전달하며 피드백 화면에도 근거를 보여준다. UTC 촬영 시각을 잘못 timezone만 제거하던 Worker 변환도 KST로 바로잡았다. 과거 저장 DB 행은 수정하지 않는다.

육아 기록 자체는 InferenceFeedback이나 학습 Job을 만들지 않는다. 실제 상태를 명시한 기존 피드백만 사용자별 학습 경로에 들어가며 mock/synthetic 제외 및 모델 승인 정책은 유지한다.

## API / DB

| API | 역할 |
|---|---|
| GET /api/care/summary | 기록 요약/입력 월령·기준/현재 참고 설정 |
| GET /api/care/profile | 내 아이 이름/추정 월령/입력일 |
| POST /api/care/profile | 내 아이 이름/현재 월령 수정, 참고 토글 보존 |
| GET /api/care/records | 사용자 소유 기록, 기본 7일, 조회 범위 최대 31일, pagination |
| POST /api/care/records | UUID 멱등 저장, feeding/sleep·시각 검증 |
| POST /api/care/records/{uuid} | expected_revision 기반 수정 |
| POST /api/care/records/{uuid}/delete?expected_revision=N | 소유권/버전 검사 후 삭제 |
| POST /api/care/preferences | context_enabled 설정 |

006_care_records.sql은 care_records, care_profiles와 emotion_events.care_context JSON nullable 컬럼을 추가한다. 이전 행은 NULL로 유지한다. 데이터 삭제·가중치 변경은 없다. PostgreSQL advisory lock으로 계정별 입력/수면 중복 검사/분석 스냅샷을 직렬화한다. DB CHECK도 종류/필수 값/수면 구간을 검증한다. 별도 extension이나 새 외부 서비스는 필요 없다.

기존 create_all만으로 emotion_events 컬럼을 추가할 수 없으므로 운영 SQL이 먼저 필요하다. 배포 전 PostgreSQL backup과 이전 migration 상태를 확인한다. API 신규 요청을 중지하고 진행 중 분석/큐를 비운 뒤 API와 backend-worker만 안전하게 정지한다. 실행 중 GPU 재학습/가중치/Job 상태는 건드리지 않는다. 006을 ON_ERROR_STOP으로 적용한 후 새 API와 분석 Worker를 함께 갱신한다. 기존 notification-worker는 결과 이벤트 포맷을 그대로 처리한다. 운영 자동 배포는 하지 않았다.

원래 정책으로 되돌릴 때 context_enabled=false만 저장하면 이후 요청의 보정을 끌 수 있다. 코드 rollback 시 006 컬럼/테이블을 삭제하지 않는다. 새 기능의 입력 기록과 기존 분석 근거를 보존한다. 먼저 중지한 서비스가 방치되지 않도록 이전 코드/이미지를 기록하고 오류별 복구 계획을 준비한다. 구체적 커밋과 명령은 배포 PC 프롬프트에 제공한다.

## 검증 / 로컬 재현

최신 회원가입/월령 변경은 SIGNUP_CHILD_AGE.md 참고. 초기 결과는 CARE_RECORDS_TEST_RESULTS.md 참고. 실제 운영 DB/가중치/키나 실제 아기 데이터에는 접근하지 않았다.

- backend/tests/test_care.py: 소유권/중복/수면 구간/수정 충돌/UTC/개인 간격/quiet 유지/불명 촬영시각/스냅샷/실제 Worker-알림 경로.
- PostgreSQL optional tests: 006 재실행, 기존 스키마 전환, DB CHECK, 동시 수면 기록 직렬화. 개발 PC에서는 DB 부재로 skip한다.
- browser: 기존 loopback review_demo.py는 임시 SQLite와 mock 사용자만 사용하며 /api/care도 연결한다. /mock/care-analysis는 실제 Worker/context/알림 저장을 실행하되 모델과 FCM/Redis 외부 경계만 모의 처리한다. 운영 main에는 /mock/* 라우트가 없다.

저장소 root에서 Python backend/tools/review_demo.py --port 8791을 실행하고, 별도 터미널 babyeye-web에서 VITE_API_BASE_URL=http://127.0.0.1:8791 설정으로 npm.cmd run dev -- --host 127.0.0.1 --port 5179 --strictPort를 실행한다. Playwright는 기존 ignored work/review-browser에 설치하고 node babyeye-web/tests/care-browser.mjs를 실행한다. 새 mock 서버에서 시작하며 반복할 때 서버를 재시작한다. screenshots/JSON은 ignored work/care-browser-results에 생성된다.

Android v1.6/versionCode7 빌드 제공. 실제 API/006/분석 Worker를 먼저 적용하고 새 앱에서 기록을 입력한다. 서명이 다르면 기존 키로 재빌드하며 앱을 임의 삭제하지 않는다.
